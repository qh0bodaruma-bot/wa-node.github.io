# Webデザイン・パターンライブラリ

国内外のWebデザインギャラリーから抽出した「デザインパターン」と「アニメーションパターン」を、
**このリポジトリ（Astro 4 + Cloudflare）にそのまま実装できる形**で管理する。

作成: 2026-08-20 / 調査対象: SANKOU!・MUUUUU.ORG・ちょうどいいWebデザインギャラリー・Web Design Garden ほか

## IDの使い方

パターンには固定IDを振ってある。実装依頼のときはIDで指定する。

```
例: 「works.astro のヒーローを DP-03 に変えて、見出しに AN-04 を入れて」
```

IDは**削除しない**。使わなくなったパターンは `【非推奨】` を付けて残す（過去の実装がIDを参照しているため）。

## このリポジトリの前提（実装時に必ず守る）

| 項目 | 現状 |
| --- | --- |
| フレームワーク | Astro 4（`astro.config.mjs`） |
| ページ遷移 | Astro `<ViewTransitions />` 導入済み（`src/layouts/BaseLayout.astro:103`） |
| スクロール表示 | `.reveal` + IntersectionObserver 実装済み（`src/layouts/BaseLayout.astro:104-152`） |
| 動きの抑制 | `prefers-reduced-motion` 対応済み（`src/styles/global.css:323`） |
| デザイントークン | `src/styles/global.css:1-24` の CSS変数（`--trust` `--action` `--accent` など） |
| 外部JSライブラリ | **現時点でゼロ**（`package.json` にアニメーション系依存なし） |

### 実装の鉄則

1. **`.reveal` で足りるなら新しい仕組みを作らない。** 既存のIntersectionObserverに乗せる。
2. **色は必ずCSS変数を使う。** 生の16進数を新規に書かない。
3. **すべての動きに `prefers-reduced-motion: reduce` の停止規則を書く。**
   アクセシビリティは和-Nodeの差別化軸そのもの（`business-docs/roles/production/CLAUDE.md`）。
4. **依存パッケージの追加は、必要性を説明してからボスの承認を取る。** 同上の禁止事項。
5. **キーボード操作とフォーカス可視化を壊さない。** ホバー専用の表現は必ず `:focus-visible` にも同じ指定を入れる。

## パターン採用の判断フロー

```
そのパターンは「LINE連携の相談をしたい人」の判断を助けるか？
  ├ NO  → 採用しない（見た目だけの装飾は、B2Bでは信頼を下げる方向に働く）
  └ YES → 実装コストは？
           ├ CSSのみ        → 実装する
           ├ 素のJS 50行以内 → 実装する
           └ 外部ライブラリ必要 → ボスに「何のために・何KB増えるか」を出して承認を取る
```

### 反対材料（この資料の使いすぎで起きること）

- **表現を足すほど、B2Bの信頼感は下がりうる。** 顧客はBtoB企業のIT担当者。派手な動きは「制作会社の自己満足」に見え、"この会社は業務システムを任せられるのか" という判断をむしろ濁らせる。凝った表現は `lab/` `demos/` 側に閉じ、コーポレート本体は静かに保つほうが受注には効く可能性が高い。
- **JSを足すほどCloudflareの配信サイズと LCP が悪化する。** GSAP + Lenis で最小構成でも約 +60KB(gzip)。Lighthouse のスコアは「アクセシビリティが売り」の会社にとって営業資料そのもの。
- **やらない場合の選択肢**: このライブラリを「実装せずに提案書の引き出しとして使う」。顧客に「こういう表現もできます」と見せるカタログとしてだけ運用し、自社サイトは現状維持にする。実装ゼロでも価値が出る使い方。
